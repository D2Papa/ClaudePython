# 테스트 기법 상세

## 목차
1. 동치 클래스 분할 (ECP)
2. 경계값 분석 (BVA)
3. 페어와이즈 (PICT)
4. WoW 검증 (엣지 케이스)
5. 제안 케이스
6. 좋은 케이스 / 나쁜 케이스

기법 이름은 워크북에서 아래 표기를 그대로 쓴다 (검증 스크립트가 이 문자열로 집계한다):
`동치 클래스 분할`, `경계값 분석`, `페어와이즈 (PICT)`, `WoW 검증`. 그 밖의 기법(`상태 전이`, `결정 테이블`, `오류 추측`, `결함 주입` 등)은 자유롭게 쓸 수 있다.

---

## 1. 동치 클래스 분할

- 입력마다 **유효 클래스**와 **무효 클래스**를 나눈다. 무효 클래스는 범위 미만, 범위 초과, 정의되지 않은 열거값, 신호 무효(invalid/timeout 플래그) 등.
- 출력 동작이 달라지는 구간도 클래스다. 예: 차속 0~10 km/h는 기능 비활성, 10~180은 활성 → 입력 범위가 하나여도 클래스는 둘.
- 클래스마다 대표값 1개면 충분하다. 같은 클래스에서 값을 여러 개 고르는 건 중복이다.
- 유효 클래스는 한 케이스에 여러 입력의 유효 클래스를 묶어도 되지만, **무효 클래스는 한 케이스에 하나만** 넣는다 — 둘 이상 넣으면 어떤 무효 입력이 반응을 일으켰는지 판정할 수 없다.

## 2. 경계값 분석

범위 `[min, max]`, 분해능 `r`(요구사항 또는 신호 정의의 최소 단위)일 때:

- **2-value (ASIL QM/A 기본)**: `min-r`, `min`, `max`, `max+r`
- **3-value (ASIL B 이상 권장)**: 위에 더해 `min+r`, `max-r`
- 출력이 바뀌는 내부 임계값(예: 10 km/h)도 경계다. `9.9`, `10.0`, `10.1`처럼 분해능 단위로.
- 경계가 "이상/초과", "이하/미만" 중 무엇인지 요구사항에서 확인한다. 불명확하면 요구사항 이슈로 올린다 — 경계값 케이스의 기대값이 바로 이 해석에 달려 있다.
- 시간 경계(타임아웃, 디바운스, 응답 시간)도 BVA 대상이다: 예 100 ms 타임아웃이면 `99 ms`, `100 ms`, `101 ms` (측정 분해능 고려).
- 한 케이스 안에서 절차 단계로 `min-r` → `min`을 연속 인가하고 단계별 기대값을 쓰는 것은 괜찮다. 단 단계마다 기대값이 따로 있어야 한다.

## 3. 페어와이즈 (PICT)

### 언제 쓰나
- 출력에 함께 영향을 주는 **독립 파라미터가 3개 이상**이고, 전체 조합 수가 실행하기에 너무 많을 때 (예: 4개 파라미터 × 3~4 값 = 100+ 조합).
- 파라미터 2개뿐이거나 전체 조합이 작으면(대략 20개 이하) 전체 조합을 쓰거나 결정 테이블로 처리하는 것이 낫다. 이 경우 페어와이즈를 억지로 쓰지 않는다.

### 모델 작성
값에는 ECP의 **대표값**(필요하면 경계 대표값)을 쓴다. BVA 값을 전부 넣으면 조합이 폭발하고, 경계는 이미 BVA 케이스로 검증된다.

```
# model_wiper.txt
Ignition:    OFF, ACC, ON
WiperSwitch: OFF, INT, LOW, HIGH
RainSensor:  NONE, LIGHT, HEAVY
VehicleSpeed: STOP, LOW, HIGH

IF [Ignition] = "OFF" THEN [WiperSwitch] = "OFF";
```

- 무효값은 `~` 접두사(예: `~INVALID`)를 붙이면 PICT가 한 행에 하나만 넣는다.
- 물리적으로 불가능한 조합은 `IF ... THEN ...;` 제약으로 제거한다. 불가능한 조합 행은 실행 불가 케이스가 되기 때문이다.
- **파라미터 이름과 값은 ASCII로 쓴다.** Windows에서 PICT는 한글 인코딩을 안정적으로 처리하지 못할 수 있다. 케이스 문서화 단계에서 한글 설명으로 바꾼다.
- 기본 2-way. 고 ASIL 핵심 기능이면 `--order 3`을 고려한다.

### 실행
```
python scripts/run_pict.py model_wiper.txt --out-json pict_wiper.json
```
PICT가 없으면 스크립트가 GitHub `microsoft/pict` 릴리스에서 받아 스킬의 `bin/`에 설치한다. 결과 JSON의 모든 행을 케이스로 만들고, 각 케이스의 기법을 `페어와이즈 (PICT)`, `pict_model`에 모델 이름을 적는다. 기대값은 행마다 요구사항에 따라 계산해 넣는다 — PICT는 입력 조합만 만들 뿐 기대값은 주지 않는다.

## 4. WoW 검증 (엣지 케이스)

ECP/BVA로 체계적으로 나오지 않는, 실제 차량·현장에서 문제를 일으키는 극단 상황. 기법을 `WoW 검증`으로 표기한다. 후보:

- 동작 중 전원 차단 / 저전압 / 재인가 후 상태 복귀
- 입력 신호 타임아웃, 메시지 누락, 값 고착(stuck)
- 여러 입력의 **동시** 변경, 상태 전이 **순간**의 입력
- 허용 최대 빈도로 스위치 토글 (디바운스·채터링)
- 초기화 직후 첫 주기, 초기값 미수신 상태
- 카운터·타이머 오버플로, 장시간 연속 동작
- 진단/고장 상태에서 다시 정상 신호가 들어오는 복구 경로

요구사항이 해당 상황의 동작을 정하고 있으면 기본 케이스, 정하지 않았으면 `제안` 케이스로 두고 요구사항 이슈에도 올린다. 모든 요구사항에 억지로 WoW 케이스를 붙이지 않는다 — 실제 위험이 있는 곳에만.

## 5. 제안 케이스

`"suggested": true`. 다음 경우에 쓴다:
- 요구사항이 다루지 않는 위험 상황 (요구사항 갭) — `gap_reason`에 설명
- 경험 기반 오류 추측
- 요구사항이 모호해 기대값이 확정되지 않은 케이스 — 요구사항 이슈와 연결

제안 케이스는 커버리지에 포함되지 않는다. 사용자가 검토 후 채택하면 `suggested`를 지우면 된다.

## 6. 좋은 케이스 / 나쁜 케이스

**나쁜 예 (실행 불가, 판정 불가)**
- 입력값: "차속을 적당히 높인다" / 예상 출력값: "정상 동작한다"
- 같은 유효 클래스에서 50, 60, 70 km/h로 세 개 — 커버리지만 부풀림
- 무효 입력 두 개를 한 케이스에 동시 인가 — 원인 판정 불가

**좋은 예**
- 테스트 목적: SRS-012 차속 하한 경계(10 km/h)에서 기능 활성 전환 확인
- 사전 조건: IGN=ON, 기능 스위치=ON, 차속 0 km/h에서 2 s 유지
- 입력값: VehicleSpeed = 9.9 km/h → 10.0 km/h
- 절차: 1) VehicleSpeed를 9.9 km/h로 설정하고 500 ms 유지 2) VehicleSpeed를 10.0 km/h로 설정
- 예상 출력값: 1단계 후 FuncActive = 0, 2단계 후 100 ms 이내 FuncActive = 1
- 사용한 테스트 기법: 경계값 분석
