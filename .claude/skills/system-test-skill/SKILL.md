# System-Test-Skill

요구사항(테스트 베이시스)으로부터 **실행 가능한** SW 시스템 테스트 케이스를 도출하고, 추적성과 커버리지를 기계적으로 검증한 Excel 워크북으로 납품한다.

이 스킬의 결과물은 A-SPICE 심사나 ISO 26262 기능안전 평가에서 증적(work product)으로 쓰인다. 그래서 "케이스가 많아 보이는 것"보다 **각 케이스가 왜 존재하는지(어떤 요구사항의 어떤 동치 클래스/경계를 검증하는지)가 추적되는 것**이 훨씬 중요하다. 심사자는 커버리지 숫자를 채우려고 만든 의미 없는 케이스를 금방 알아보고, 그런 케이스는 오히려 테스트 명세 전체의 신뢰도를 깎는다.

## 참고 파일 (필요할 때 읽기)

| 파일 | 언제 읽나 |
|---|---|
| `references/standards.md` | A-SPICE / ISO 26262-6 요건과 산출물 항목의 대응 관계가 필요할 때 (처음 한 번은 읽을 것) |
| `references/techniques.md` | BVA·ECP·PICT·WoW 검증의 구체 규칙과 좋은/나쁜 케이스 예시 — 케이스 설계 전에 읽을 것 |
| `references/spec_schema.md` | `build_workbook.py`에 넘길 JSON 형식 — 워크북 만들기 직전에 읽을 것 |

## 스크립트

- `scripts/run_pict.py` — PICT를 찾거나(없으면 GitHub `microsoft/pict`에서 받아 설치) 모델 파일을 실행해 조합 결과를 JSON/TSV로 저장한다.
- `scripts/build_workbook.py` — 케이스 JSON을 검증(추적성·커버리지·필수 기법·중복·모호한 기대값)하고 Excel을 만든다. 오류가 하나라도 있으면 파일을 만들지 않고 오류 목록을 출력한다.

둘 다 Python 3.8+가 필요하고, 워크북 생성에는 `openpyxl`이 필요하다 (`pip install openpyxl`).

## 작업 절차

### 1. 입력 확인

- **테스트 베이시스**: 요구사항 문서(문서, 표, 텍스트 어느 형식이든). 요구사항마다 ID가 있으면 그대로 쓰고, 없으면 `TB-001`처럼 부여한 뒤 원문 문장과의 매핑을 워크북에 남긴다 — 추적성의 출발점이 ID이기 때문이다.
- **테스트 케이스 양식**: 사용자가 양식(xlsx 등)을 줬다면 그 양식의 열 구성과 서식을 따른다. 없으면 아래 기본 열을 쓴다.
- **ASIL**: 요구사항에 ASIL이 있으면 기록한다. ASIL이 높을수록 경계값을 3-value로 촘촘하게 잡는 등 설계 강도가 달라진다 (`references/techniques.md`).
- 정보가 모자라 실행 가능한 케이스를 못 만드는 요구사항(값 범위·단위·타이밍이 정의되지 않음 등)은 추측으로 메우지 말고 **요구사항 이슈**로 기록한다. 추측한 값으로 만든 케이스는 실행할 수 없거나, 더 나쁘게는 틀린 기대값으로 합격 판정을 낸다.

### 2. 기본 열 (양식이 없을 때)

| 열 | 내용 |
|---|---|
| 테스트 케이스 ID | `STC-F-001`(기능), `STC-NF-001`(비기능) |
| 테스트 베이시스 ID | 추적 대상 요구사항 ID (여러 개면 쉼표) |
| 테스트 목적 | 무엇을, 어떤 클래스/경계에서 확인하는지 한 문장 |
| 사전 조건 | 실행 전에 맞춰야 할 상태 (실행 가능성을 위해 추가) |
| 입력값 | 신호/파라미터명 = 구체적 값 + 단위 |
| 절차 | 번호 매긴 단계 |
| 예상 출력값 | 관측 가능한 구체적 값·상태·시간 한계 |
| 사용한 테스트 기법 | 경계값 분석 / 동치 클래스 분할 / 페어와이즈 (PICT) / WoW 검증 / 기타 |
| 제안 | 스킬이 추가로 제안한 케이스면 `제안` |

### 3. 요구사항별 분석

각 요구사항에 대해 먼저 다음을 정리한다 (워크북에는 안 들어가도 되지만 케이스 설계의 근거다):

1. **기능 / 비기능 분류** — 비기능: 타이밍·응답시간, 성능·부하, 메모리·자원, 시동/종료 시간, 강건성, 진단·고장 처리, 신뢰성 등.
2. **입력·출력 도메인** — 입력 신호/파라미터, 값 범위, 단위, 분해능, 상태.
3. **동치 클래스** — 유효 클래스와 무효 클래스를 모두. 각 클래스에 대표값 하나.
4. **경계** — 각 범위의 경계와 그 바로 바깥/안쪽 값 (분해능 단위).
5. **조합 파라미터** — 출력에 함께 영향을 주는 독립 파라미터가 3개 이상(또는 값이 많은 2개)이면 페어와이즈 후보.

### 4. 케이스 도출

- **동치 클래스 분할, 경계값 분석은 입력 도메인이 있는 모든 요구사항에 필수.** 입력 도메인이 정말 없는 요구사항(예: "부팅 시 버전 문자열을 표시한다")은 JSON에 `bva_ecp_na_reason`을 적어 예외 사유를 남긴다. 사유 없이 빠지면 검증 스크립트가 오류를 낸다.
- **페어와이즈는 적용 가능한 경우에만, 반드시 PICT로.** 손으로 조합표를 만들지 않는다 — 수작업 조합은 쌍 커버리지가 보장되지 않아 "페어와이즈를 적용했다"는 주장이 거짓이 될 수 있다. PICT 모델 작성 → `python scripts/run_pict.py model.txt --out-json result.json` → 결과의 **모든 행**을 각각 케이스로 만든다 (행을 빼면 쌍 커버리지가 깨진다). PICT를 설치·실행할 수 없으면 페어와이즈 케이스를 만들지 말고 사용자에게 그 사실을 알린다. 모델 문법과 팁은 `references/techniques.md`.
- **엣지 케이스는 기법을 `WoW 검증`으로 표기한다.** 경계값·동치 클래스로 자연스럽게 나오지 않는 극단 상황 — 동작 중 전원 차단/재인가, 신호 타임아웃·끊김, 입력 동시 변경, 최대 빈도 토글, 초기화 직후 첫 주기, 카운터 오버플로, 상태 전이 순간의 입력 등. 요구사항에 근거가 있으면 기본 케이스, 요구사항에 명시되지 않은 상황이면 `제안`으로 표시한다.
- **제안 케이스** — 요구사항에서 직접 도출되지 않았지만 스킬이 가치 있다고 판단해 추가한 케이스(요구사항 갭, 오류 추측, 명시되지 않은 엣지 등)에는 `"suggested": true`를 둔다. 제안 케이스는 커버리지 산정에서 빠진다 — 사용자가 채택하지 않을 수 있으므로, 커버리지 100%는 제안 없이도 성립해야 한다.

### 5. 품질 기준 (모든 케이스에 적용)

케이스 하나하나가 다음을 만족해야 한다. 만족하지 못하면 고치거나 지운다.

- **실행 가능**: 테스터가 다른 질문 없이 그대로 실행할 수 있다. 입력은 구체적 값과 단위, 절차는 단계별, 기대값은 관측 가능한 구체적 값/상태/시간 한계. "정상 동작한다", "적절히 처리한다" 같은 기대값은 판정이 불가능하므로 금지.
- **고유한 목적**: 다른 케이스와 같은 클래스·경계를 같은 방식으로 반복하지 않는다. 커버리지를 위해 같은 내용을 ID만 바꿔 늘리지 않는다.
- **추적 가능**: 존재하는 베이시스 ID에 연결된다 (요구사항 갭을 다루는 제안 케이스는 `gap_reason`으로 설명).
- **기대값의 근거가 요구사항에 있다**: 요구사항이 정하지 않은 값을 기대값으로 지어내지 않는다. 필요하면 요구사항 이슈로 올리고, 확인 전까지 해당 케이스는 제안으로 둔다.

### 6. 검증과 워크북 생성

1. `references/spec_schema.md`를 읽고 전체 결과를 JSON으로 작성한다.
2. 실행: `python scripts/build_workbook.py spec.json -o <출력경로>.xlsx` (양식이 있으면 `--template 양식.xlsx`)
3. 오류가 나오면 **케이스를 고쳐서** 다시 실행한다. 오류를 없애려고 의미 없는 케이스를 추가하거나 `bva_ecp_na_reason`을 남용하지 않는다 — 그건 검증을 속이는 것이고 심사에서 그대로 드러난다.
4. 오류 0건이 되면 워크북이 생성된다. 시트 구성:
   - `기능 테스트`, `비기능 테스트` — 케이스
   - `추적성 매트릭스` — 베이시스 ↔ 케이스 양방향 (A-SPICE의 bidirectional traceability)
   - `커버리지 요약` — 베이시스 커버리지 %, 기법별 케이스 수, 검증 결과
   - `PICT 모델` — 사용한 모델과 결과 행 수 (페어와이즈를 쓴 경우)
   - `요구사항 이슈` — 모호·누락된 요구사항 (있는 경우)
   - `베이시스 ID 매핑` — ID를 부여한 경우 원문과의 매핑

출력 경로를 사용자가 정하지 않았으면 작업 디렉터리의 `output/<프로젝트명>_SystemTestSpec.xlsx`.

### 7. 사용자에게 보고

짧게:
- 워크북 경로
- 베이시스 수, 커버리지 %, 기능/비기능 케이스 수, 제안 케이스 수
- 기법별 케이스 수 (BVA / ECP / PICT / WoW 검증)
- 요구사항 이슈가 있으면 그 목록 — 사용자가 답해야 확정할 수 있는 것들이므로 가장 중요하다
